ReActAgent

ReAct 模式中，大语言模型需要经历 思考-行动-观察 的流程，而第四章中我们实现的 ReActAgent，每一个循环分别三次调用 LLM，我们需要让 ReActAgent 继承抽象类 Agent。

grill-with-docs 的建议

使用 /grill-with-docs 设计时，它提出了以下问题，我把我认为比较重要的问题贴上来：

ReflectionAgent 需要集成工具（Tool）吗？

看 reflectionPrompt.py 里的三个模板：

  1. initial — 根据 {task} 生成答案
  2. reflect — 根据 {task} + {content} 做自我批评
  3. refine — 根据 {task} + {last_attempt} + {feedback} 改进答案

这三个阶段都没有工具调用的语义。这是一个纯”生成 → 自省 → 改进”的链路，和 ReActAgent 的”思考 → 行动 → 观察”完全不同。

我的建议：不需要集成 ToolRegistry。ReflectionAgent 的核心价值是自我反思与迭代优化，工具调用是 ReActAgent
的职责。加工具反而让两个 Agent 的边界模糊。

反思循环次数——执行一轮”生成→反思→改进”就结束，还是支持多轮迭代？

ReActAgent 有 max_iterations（默认 5）来控制 Thought-Action 循环。ReflectionAgent 类似地可以：

  • 方案A：固定一轮 —— generate → reflect → refine，结束。简单直接。
  • 方案B：可配置多轮 —— 把上一轮的 refine 结果再送入 reflect → refine，循环直到 max_iterations 或者 feedback
    中模型自己判定”已经够好了”。

我的建议：方案B，可配置多轮，默认 2-3 轮。反思的本质就是反复打磨，只做一轮有时候改进不够明显。保留一个 max_reflections
参数（默认 2），让调用方可以调整。

构造函数参数设计

ReActAgent 的构造函数签名为：

def init(self, name, llm, system_prompt=None, config=None,
tool_registry=None, max_iterations=5, is_stream=False, verbose=True)

ReflectionAgent 目前是个空壳。按我们的决定，它需要这些参数：

│ 参数 │ 建议 │

│ name, llm, system_prompt, config │ 继承基类，保留 │
├──────────────────────────────────┼────────────────────────────────────────────────────┤
│ tool_registry │ 不要 │
├──────────────────────────────────┼────────────────────────────────────────────────────┤
│ max_reflections │ 加，默认 2 │
├──────────────────────────────────┼────────────────────────────────────────────────────┤
│ is_stream │ 不要，你已明确不需要流式 │

我的建议是：

def init(self, name, llm, system_prompt=None, config=None,
max_reflections=2, prompts=None, verbose=True)

  • prompts 默认 None，运行时取 DEFAULT_PROMPTS，允许用户自定义三个阶段的提示词
  • max_reflections 控制反思-优化循环的最大次数
  • verbose=True 打印每轮的反思结果和优化结果

循环终止条件

多轮反思循环需要一个终止条件，否则会跑到 max_reflections 上限。有两种思路：

  • 方案A（纯计数）：跑满 max_reflections 轮，不提前终止。简单稳定，每轮都在前一轮基础上打磨。
  • 方案B（智能判定）：每轮 reflect 之后检查 feedback 内容，如果模型在 feedback 中明确表示”答案已经足够好了 /
    没有更多改进空间”，就提前终止，避免浪费 token。

我的建议：方案A，纯计数。让模型在 prompt 里自己判断”还需要不需要改进”不可靠，容易过早终止或者反复纠结。而且
max_reflections 默认只有 2，每轮 refine 都在进步，不差那一轮。简单可预测。

(这里由我出面采用可选择智能判断+纯计数：我们加上一个输入参数auto_finish:bool，如果true就支持智能终止，如果false就纯计数终止)

好，加 auto_finish: bool，默认 False（纯计数），设为 True 时智能判定提前终止。

run() 的返回值设计

ReActAgent 的 run(input_text) -> str 只返回最终答案。但对于 ReflectionAgent，中间产物（初始答案、每轮的
feedback、每轮的优化结果）也有价值。

  • 方案A（纯字符串）：run(input_text) -> str，只返回最终 refined 答案，和 ReActAgent 保持一致。
  • 方案B（结构化返回）：run(input_text) -> dict，返回 {“final_answer”: …, “initial_answer”: …, “reflections”:
    [{“feedback”: …, “refined”: …}, …]}，让调用方能拿到完整的反思链路。

我的建议：方案A。和基类 Agent 的签名 -> str 保持一致，而且 SimpleAgent、ReActAgent 都返回 str。中间产物可以通过
verbose=True 打印出来，调用方如果真想拿到中间结果，可以看 history。

auto_finish=True 时的智能终止机制

如果开启智能终止，需要一个明确的信号来判定”不用再改了”。有两种做法：

  • 方案A（prompt 内嵌）：在 reflect 提示词中要求模型，如果认为无需改进就输出特定标记（比如
    [NO_IMPROVEMENT_NEEDED]），Agent 解析到就终止。
  • 方案B（对比判定）：把 refined 答案和上一轮答案做相似度对比（比如用 LLM 或简单字符串相似度），如果变化很小就终止。

我的建议：方案A。方案B 要么引入额外的 LLM 调用（浪费），要么用字符串相似度不可靠。方案A 只需在 reflect prompt
里加一句”如果你认为答案已经完美无需修改，请回复 [NO_IMPROVEMENT_NEEDED]”，然后正则匹配即可，零额外成本。

历史记录管理

ReActAgent 会在 _history 中保存用户输入和最终回复。ReflectionAgent 有多轮中间产物（initial answer、每轮的
feedback、每轮的 refined answer），这些是否都要存入 self._history？

  • 方案A（只存最终）：和 ReActAgent 一样，只存 user input + final answer，保持 history 干净。
  • 方案B（全存）：把每轮的反思和优化都作为 assistant message 存入 history，完整记录思考链路。

我的建议：方案B。反思过程本身就是 Agent 的”思考”，存入 history 让后续对话有完整的上下文。而且 ReflectionAgent
没有工具调用，不会让 history 膨胀过快。

auto_finish 的判定逻辑细节

方案A 说了在 reflect prompt 中要求模型输出 [NO_IMPROVEMENT_NEEDED] 标记。具体怎么实现？

  • 做法①：在 reflect 的 prompt 模板里追加一句”如果你认为无需改进，输出 [NO_IMPROVEMENT_NEEDED]”，然后正则匹配。这会改动
    DEFAULT_PROMPTS。
  • 做法②：不改 DEFAULT_PROMPTS，在 Agent 内部拿到 reflect 结果后，额外调一次 LLM
    小请求判定”这反馈是否意味着无需改进”。多一次 LLM 调用。
  • 做法③：不改 prompt 模板，直接用正则检测 reflect 结果中是否包含类似”完美/无需修改/已经很好”等关键词。不可靠。

我的建议：做法①。改动最小，零额外成本，判定最可靠。DEFAULT_PROMPTS[“reflect”]
末尾加一句类似”如果答案已经足够好、无需改进，请只回复 [NO_IMPROVEMENT_NEEDED]”。

每轮 refine 的消息构建方式

ReflectionAgent 的三个阶段是三次独立的 LLM 调用。以 max_reflections=2 为例：

第1轮: initial(生成) → reflect(反思) → refine(优化)
第2轮: reflect(再反思) → refine(再优化) → 返回

每轮 reflect 的输入是 {task} + {content}（上一步的答案），refine 的输入是 {task} + {last_attempt} + {feedback}。

那第二轮 reflect 的 {content} 应该传什么？

  • 方案A（只传最新）：传上一轮的 refined 答案，不带上之前的 feedback。每轮独立。
  • 方案B（累积上下文）：把之前的 initial + feedback₁ + refined₁ 拼成一个上下文，让模型看到完整演进过程。

我的建议：方案A。refine 已经把 feedback 吸收了，输出的 refined 答案就是”综合了反馈的结果”，下一轮 reflect
只需要审视这个最新版。累积上下文会让消息越来越长，且模型可能被旧反馈干扰。

verbose=True 时的日志输出格式

每轮反思循环中会输出哪些信息？参考 ReActAgent 的 verbose 会打印 Thought、Action、Observation。ReflectionAgent
的日志同样需要清晰展示反思链路。

我建议每轮输出类似：

[ReflectionAgent] 第 1/2 轮反思
📝 初始答案: <initial answer 摘要>
🔍 反思反馈: <feedback 摘要>
✨ 优化结果: <refined answer 摘要>

system_prompt 参数的处理

基类 Agent.init 接受 system_prompt 参数，但 ReActAgent 实际上忽略它，始终用自己的 REACT_PROMPT。ReflectionAgent
的三个阶段各有自己的提示词（来自 prompts 参数的三个 key），跟 system_prompt 没有直接关系。

我的建议：忽略 system_prompt，和 ReActAgent 保持一致。prompts 参数完全替代 system_prompt 的作用。

prompts 参数的合并策略

用户传入自定义 prompts 时，是完全替换 DEFAULT_PROMPTS，还是合并（只覆盖传入的 key，未传入的保持默认）？

比如用户只传 {“reflect”: “自定义反思提示词”}，那 initial 和 refine 是否保留默认？

我的建议：合并策略。更灵活，用户只需覆盖他想定制的部分。

初始化

除了 Agent 基类中包含的输入参数，我们还需要给定：

  • max_steps：最大迭代次数，因为 ReAct 需要多次观察才能得出最 LLM 认为最完备的响应；
  • custom_prompt：让用户能够自定义自己的 ReAct 提示词模板；
  • verbose：是否将 思考-行动-观察 的全过程打印出来；
  • is_stream：是否流式输出。

_process_response

回想第四章中的做法，让 LLM 进行 think 之后，我们需要从冗长的结构化 JSON 输出中提取出我们事先让 LLM 输出的关键词，也即 Thought、Action 和 Finish。

grill-with-docs 的建议

使用 /grill-with-docs 设计时，它提出了以下问题，我把我认为比较重要的问题贴上来：

Plan 阶段的输出解析

DEFAULT_PLANNER_PROMPT 要求 LLM 输出：

[“步骤1”, “步骤2”, “步骤3”, …]

怎么把这个字符串解析成真正的 Python list？

  • 方案A（ast.literal_eval）：安全解析，只接受字面量。但如果 LLM 输出格式稍有偏差（多了注释、少了引号）就直接失败。
  • 方案B（正则提取）：用 re.findall 匹配 “…” 字符串，容错性高。
  • 方案C（先 ast 后正则兜底）：先尝试 ast.literal_eval，失败则用正则提取引号内字符串。

我的建议：方案C。ast.literal_eval 正常情况最可靠，正则做兜底避免 LLM 格式不稳定导致整个 Agent 崩溃。

所有子任务执行完后，如何产出最终答案？

执行循环按计划逐步产出每个步骤的结果。执行完最后一步后：

  • 方案A（最后一步即最终答案）：执行完计划中所有步骤后，最后一步的结果就是最终答案。综合能力交给规划器——如果用户问的问题
    需要综合，规划器自然会把”总结”作为最后一步。
  • 方案B（最终汇总调用）：所有步骤执行完后，额外调一次 LLM，把所有步骤及其结果汇总成一个完整答案。

我的建议：方案A。规划器的职责就是把问题拆成合理的步骤序列，最后一步天然可以承担”给出最终答案”的角色。方案B 每次多花一次
LLM 调用，且与规划器的职责重叠。

步骤间的历史累积方式

Executor prompt 有一个 {history} 占位符。随着步骤推进，{history} 需要逐步填充。有两种做法：

  • 方案A（扁平累积）：{history} 是一段文本，格式为：
    步骤1: [步骤1描述]
    结果1: [步骤1的结果]

步骤2: [步骤2描述]
结果2: [步骤2的结果]

  • 方案B（只传上一步结果）：{history} 只包含上一步的结果，不附带更早的历史。

我的建议：方案A。后续步骤可能需要前面所有步骤的上下文（比如步骤3需要步骤1和步骤2的结果）。方案B
信息丢失，可能让后续步骤做出错误判断。

run() 的返回值设计

和 ReflectionAgent 一样的问题：

  • 方案A：run(input_text) -> str，只返回最终答案（最后一步的结果），和基类一致。
  • 方案B：run(input_text) -> dict，返回 {“final_answer”: …, “plan”: […], “step_results”: […]}
    让调用方能拿到完整执行链路。

我的建议：方案A。和 ReflectionAgent、ReActAgent 保持一致，只返回 str。中间产物（计划列表、每步结果）通过 verbose=True
打印，也可以通过 get_history() 追溯。

Plan 解析失败处理

选择：直接报错返回，不做兜底。

ast.literal_eval 和正则都失败，说明 LLM
输出的格式严重偏离要求。不降级为”整个问题当单步执行”，那样会隐藏问题根源。让调用方看到明确的错误信息。

self._history 管理

选择：保存（用户输入 + 计划 + 每步结果），全部标为 assistant。

[0] user: “用户原始问题”
[1] assistant: “📋 计划: [‘步骤1’, ‘步骤2’, ‘步骤3’]”
[2] assistant: “步骤1: … 结果: …”
[3] assistant: “步骤2: … 结果: …”
[4] assistant: “步骤3: … 结果: …”

和 ReflectionAgent 的全量存储策略一致，提供完整追溯链。

system_prompt 参数

选择：忽略。和 ReflectionAgent 一致，planner/executor 提示词完全替代 system_prompt 的作用。

verbose 输出格式

选择：中文日志，沿用 ReflectionAgent 风格：

📋 计划 (3 步):
1. 搜索相关数据
2. 计算统计指标
3. 给出最终结论

— 执行步骤 1/3 —
✅ 步骤 1 完成: <摘要>

— 执行步骤 2/3 —
✅ 步骤 2 完成: <摘要>

— 执行步骤 3/3 —
✅ 步骤 3 完成: <摘要>
🏁 最终答案: <最后一步结果>

最终完整设计汇总

PlanAndSolveAgent
├── 构造函数: (name, llm, system_prompt=None, config=None, verbose=True)
├── run(input_text) -> str:
│ ├── 阶段1 (_plan): LLM 生成步骤列表
│ │ ├── 解析: ast.literal_eval, 失败 → regex 兜底, 都失败 → 报错
│ │ └── 空列表 → 报错
│ ├── 阶段2 (_solve): 顺序执行每个步骤
│ │ ├── 每次调用 executor prompt，传入 {question}, {plan}, {history}, {current_step}
│ │ ├── history 扁平累积: “步骤N: … \n结果N: …”
│ │ └── LLM 返回 None → 中止，返回已累积结果
│ ├── 返回: 最后一步的结果 (str)
│ └── history: 全量保存 user输入 + 计划 + 每步结果

PlanAndSolveAgent 类的设计

第四章中，我们曾经构建过简易的 Plan-and-solve 模式的 Agent，其主要运行逻辑是：1.（Plan）首次调用 LLM，将初始任务拆分成若干个子任务；2.（Solve）对于若干个子任务，均调用 LLM 以解决，解决完所有子任务后，也就是完成了初始任务。

之后的就自己去看吧，与第四章并无本质区别。

总结

本章内容与第四章相似，我们仍然以从零到有构建四种 Agent 为终极目标，但比起第四章的即兴式编写代码，我们的开发路径遵照 底层 => 模板 => 成品 ，将上下文管理、大模型参数配置、Agent 的构建等进行了标准化，以这些开发成果为基础构建了一套最基本的 Agent 框架。

在 core 包内，我们从底层上对 Agent 进行了支持：标准的上下文存储对象 Message 将上下文的格式由简单的字符串固定为了严格的对象；我们构建了 LLM 参数统一配置中心 Config，避免了 LLM 参数的分散配置；随后我们使用 openAI 包，消防第四章的 HelloAgentLLm 类，构建了一个大模型调用接口 LLM；最后，我们构建了一个 Agent 抽象类，为构建一个 Agent 提供了规范。

在 tool 包内，我们主要对两种工具进行了支持：对象类和函数类。对于对象类，我们也构建了一个抽象类 Tool 作为工具的基类。而对于工具管理上，我们构建了一个 ToolRegistry，对工具进行统一的注册发现、管理和调用。随后，我们基于 Tool 接口和 Callable 函数引用构建了几个工具，并进行了测试。

在 agent 包内，我们基于 Agent 接口，对第四章中构建过的四种 Agent 进行了重构，使每一种 Agent 有着统一的构建方式和使用方法。

不过，当前的这个框架仅仅完成了最简单的功能，还有相当多的拓展空间，比如记忆、上下文工程、Agent 协议等，这些将在后续的章节中进行。
