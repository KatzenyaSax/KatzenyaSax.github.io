本章任务：

  • Cli：构建一个基本的客户端，能够成功调用 LLM ，并解析 LLM 流式返回的结果

  • ReAct(Reasoning and Action)：着重于实现如何让模型在执行过程不断根据当前状况动态地更新行动计划；

  • Plan-and-Solve：着重于构建模型的规划能力；

  • Reflection：模型的反思能力。

ReActAgent 指导思想

我们之前定义的 HelloAgentLLM 类，通过 think 函数就可以进行单一提问单一回答。而ReAct 是 think 函数的反复调用者，每次得到 Observation 写入历史后，重新调用 think 函数，直到不再调用。

所以 ReActAgent 和 HelloAgentLLM 的关系是什么呢？ReActAgent 内部包含 HelloAgentLLM 对象，用于运行最原子化的 LLM 调用流程。

Plan-and-Resolve：Planner

LLM 如何才能拥有 将复杂问题拆分成若干子问题 的能力？这一点与 ReAct 是有着显著区别的。

我们构建的 ReAct 倾向于反复调用 LLM，试图通过上下文的迭代来命中预期，也就是说前 n-1 次调用 LLM 相当于只是给第 n 次调用 LLM 做准备工作。

而 plan-and-resolve 模式中，我们力求的是分为两个阶段解决问题：

  1. 第一次让 LLM 进行 plan，选定所有需要的工具和顺序，并将其作为结构化输出封装成 PLAN；

  2. 第二次拿着封装好的 PLAN，根据工作流循环让 LLM 调用工具。

这种方式每次循环都解决一个简单的子问题。

此外，采用这种模式将规划流程标准化，即使 LLM 本身就有着很强的规划能力，也大概率能够在此基础上进一步最终执行的准确度。

Reflection

Memory

为什么需要 Reflection？就是赋予大模型反思自己的回答有无纰漏，从而进行改进的能力。我们之前构建的 Agent，不管是基于 ReAct 模式还是 plan-and-resolve 模式，都是一旦完成就退出进程了，对于此前的解答并没有进行检查。

问题是，如何获取之前的解答呢？我们之前定义的两个 Agent，都是通过一个 run 函数直接调用的，特别是 PlanAndResolveAgent 的 run 函数，里面甚至有局部变量 history 作为上下文，一旦函数结束了，上下文就释放了。

所以，对于一个合格的 Reflection 机制，最先需要实现的功能就是：全局的 Memory 记忆，他必须能够跨会话地读取到上下文，才能进行后续的反思。

构建也很简单，实则就是一个 Stack，其核心是自身的成员变量 self.records: List[Dict[str, Any]]

总结

本章构建了三种经典 Agent 范式。

我们通过先构建一个符合 OpenAI 规范的基本 LLM 调用接口 HelloAgentLLM，实现了对 LLM 进行调用以及处理 LLM 的流式响应。

通过赋予 LLM 使用工具从而与外界交互的能力，我们构建起了 ReAct 模式 Agent，这种模式更专注于通过观察与外界的交互从而决定下一步的行动，所以如何为 LLM 构建使用工具的环境也是其中一个核心课题。适合需要探索性的任务。

随后，我们实现了一个 Plan-and-Resolve 模式 Agent，解决了实现让 LLM 将复杂问题拆解 这一难题。通过分别注入标准化的提示词，强制让 LLM 分别执行 plan 与 execute 两个阶段，让 LLM 的思路更加结构化和稳定化，适合需要经过逻辑分析、内部推理密集的任务。

最后，基于 赋予 LLM 反思能力，我们构建了 Reflect 模式的 Agent，该种模式着重于让 LLM 拆解自己以前的回答，发现问题并尝试优化，能够显著提升解答质量。适合需要高质量和高精度的解答任务。
