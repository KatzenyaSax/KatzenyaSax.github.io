五大基本类型、三种特殊类型

Redis 共有 5 种基本数据类型：String（字符串）、List（列表）、Set（集合）、Hash（散列）、Zset（有序集合），可供用户定义和使用。

除了 5 种基本的数据类型之外，Redis 还支持 3 种特殊的数据类型：Bitmap、HyperLogLog、GEO。

String

最简单的 k-v 形式，v 的字符串是 redis 自己实现的一种数据结构简单动态字符串 SDS，特点是除了可以保存文本数据，还可以保存二进制、整型数据。

由于是最简单的 k-v 形式，用于存储“占位”信息很方便，比如 token、access 等。

而 String 如果是整型的 value，还可以直接使用计算方法，因此需要计数时也很好用。

除此之外，直接存序列化后的对象字符串也可以，比 Hash 省空间。

其底层实现为：SDS。

List

Redis 中的 List，底层是链表的形式存的，Redis 自己实现了一个双向链表（虽然最终不直接使用双向linkedList）用来存 List。

相比起 String 最简单的 k-v 一个对一个的形式，List 则是一个 k 对应多个 v，多个 v 就以双向链表的形式存在。如图：

自带的 LRANGE 很适合分页查询。

但是注意，List 归根结底从来只有一个 k，所以对 List 设置的 ttl 会覆盖整个 v 双向链表。

底层实现：quickList

双向 linkedList，每个节点都维护前驱、后继节点太浪费空间，而且缓存不友好。

quickList 则不再使用一个节点单独维护，而是把一部分连续的元素聚合成列表，列表再独享一个，然后列表之间再组成链表

比如这样：

这样最大的好处，就是灵活：一个节点要插入、删除、修改，那么只操作其中一个 quickListNode 的 list 即可，其余节点则不需要再操作了。

Hash

Hash 不再是简单的一个 k，而是多个 String 的 k-v 对形式，如图：

可以看到，一个 Hash 内不包含了若干 k-v 对，每个 k-v 对享受独立的 ttl，这是和 List 不同的。

当然，Hash 更适合的是映射一个对象。

底层实现：ListPack+链表

其实 Hash 就和 Java 的 HashMap 差不多，如今 redis 的 Hash 有两种底层实现，分别是 ListPack、HashTable。

ListPack 最简单，它竟然直接把每一对 k-v 同时存到一个线性表里，即 [k0, v0, k1, v1, ..., kn, vn]，这种方式适合于少量的 k-v，节省时空消耗，但是不适合量大的情况。

HashTable 和 Java 里的没区别，线性表+链表，先算哈希值存入 Dict，等发生哈希冲突了再转链表。

两种方法会从 ListPakc 到 HashTable 单向切换，k-v 对数超过 512；或者某个 k、v 的字符数超过默认 64 字节时就会发生转变，且不会再降级为 ListPack。

为什么有 64 字节限制

ZipList 本质上是连续分配的线性表，每个格子大小就是 64 字节，如果要存超过 64 字节的元素，要么截断，要么占用下一个格子两个格子一起存一个元素，但是那是不允许的，所以要转成链表，链表的节点大小可以动态分配，才能容纳超过 64 字节的元素。

Set

Set 也是一个 k-v 形式，但是类似于 List、区别于 Hash：Set 也是一个 k 对应多个 v 的形式，v 却是以集合方式存在，如图：

可以看到，相比起 List 每个 v 对应索引，Set 完全不含，因为 Set 不是有序的，而只是用于表达：一群不重复的元素，和所有语言中的 set 概念一样。

Set 可以很轻松地处理需要求交集、并集的场景，比如朋友圈点赞、评论的用户，其他用户看到好友、非好友的时候，展示不同的昵称。

和 List 一样，ttl 覆盖所有元素。

底层实现：Intset + HashTable

和 Hash 一样，数据量小（默认512）的时候，用有序的线性表直接存每个元素。数据量大了之后转 HashTable。

Set 怎么实现去重？数据量小的时候，线性表直接二分查找看有没有一模一样的，这就是为什么要保持有序。

而如果是 HashTable 就简单了，发生哈希冲突时，直接丢弃新来的。

ZSet

ZSet 就是 Sorted Set，是有序的，如图所示：

可以看到，比起 Set 的 v 只含元素，ZSet 的每个元素包含另一个因素：score，按照 score 排序。

但是需要注意，元素不能相同，但 score 可以相同。

应用场景：需要排行的场景。

底层实现：ZipList + SkipList

和其他类型一样，数据量小和数据量大的时候分别用不同的结构，ZipList 和 SkipList。

ZipList 本质上就是一个线性表，根据 score 有序地同时存元素和 score，比如 [v1, 10, v2, 20, v3, 30, ......]，当然，最大存储元素为 128，数据量超过时，或者有元素大于 64 个字节时，单向转为 SkipList。

SkipList 这里不讲，在下面 Redis 性能里面继续分析 SkipList 性能优越在哪。

BitMap

位图，用 1、0 表示某种状态，且直接用的二进制，很省空间。

底层是 string 类型你敢信吗，基于 SDS 但是不读取为 string，只关注其中二进制。

场景：例如统计活跃用户、标识用户点赞过等。

HyperLogLog

并非 redis 的显式类型，而是一种算法，redis 只是实现了部分功能。

其形式也是多 k-v 形式的，k 可以视作某种标签，v 则是数量。

HyperLogLog 的真正优势在于空间花销，只需要 12k 的空间就能存储接近2^64个不同元素，但是带来了错误率，有一定的计数误差。

Redis 性能

Redis 为什么快？

  1. 纯内存操作；

  2. 单线程模型，虽然 redis 服务是单线程，但是实现了多路 I/O 复用，所以既有性能又有安全；

  3. 数据类型的底层实现性能异常优秀；

  4. Redis 自有的 RESP (REdis Serialization Protocol) 协议简单高效。

底层数据结构

Redis 底层的数据结构性能非常优秀，重点的有 Rehash、SkipList、QuickList 等。

SDS

SDS 本质上是一个包含字符数组的对象，它显式地记录了自己的长度（所以可以实现 O(1) 级别的长度获取）；并且遍历时严格按照 for(strlen)而非遇到 ‘\0’ 时结束（这使其二进制安全）。

除此之外，它还在空间分配和释放时作出改进。分配空间时，会尝试分配更多空间，字符数组小于 1mb 时分配两倍空间、大于 1mb 时多分配 1mb，这使得空间不足的问题得到较好解决。而在释放上，SDS 遵循绝不减少空间、只增加空间的策略，除非把我杀掉。

为什么不使用 C 语言写的 char* ？因为恰好不满足 SDS 的四个优点，甚至还有缺陷。比如需要遍历 O(n) 才能得到 strlen、遇到 ‘\0’ 才结束导致二进制不安全、频繁 malloc、容易空间不足导致出问题。

Dict & Rehash

Dict 字典，可以用于维护一个哈希表；Rehash 则赋予哈希表重新分配长度的能力。Set、Hash、ZSet 都用到了 Dict 和 Rehash。

Rehash 这种数据结构有一点有意思，其扩容是渐进式的。什么意思？一张 dict 的长度，如果我们知道它最终会成长为千亿级别，但是仅仅在现在，它的长度还用不到那么高，显然直接给这个 dict 分配千亿长度很蠢，它应该只满足现在的需求，然后慢慢成长。

渐进式扩容，dict0 不够用了，就申请一个 dict0 两杯长度的 dict1，dict0 的元素重新计算哈希值加入 dict1，全部计算完后 dict0 释放，dict1 就是新的 dict0。

单线程模型

Redis 4.0 前

Redis 用 IO 多路复用监听 socket 处理客户端请求，由于全是内存操作，所以性能极为优异；而又因为 Redis 使用一个主要单线程处理所有就绪的 socket，因此甚至不需要担心并行下的锁问题，本质上是极快的串行。

捋一下逻辑，我们假设一个 redis 服务连接了若干个客户端，客户端随时有可能找 redis 读写，但是 redis 主线程只管读写数据，不管连接、请求、收发，这些谁来管？其实是操作系统内核的活。

客户端要和 Redis 建立长连接，向下请求 Linux 内核帮忙，内核查看 redis 连接没有问题，就维护一个Socket 文件描述符（fd），表示已经和 redis 连接好了，有什么事把消息发到 socket 缓冲区，内核通知 redis 就行。所以这个时候，redis 还没有真正开始干活。

当然，redis 知道有客户端和自己连接了也不是什么都不干，它会把这个 socket 加入到自己的监控区，然后和其他 socket 一样接受通过多路 IO 服用程序的监听。

当然，客户端没有请求的时候，redis 内核就耍起，等真的有请求了，Linux 内核就把 redis 内核唤醒，redis 单线程内核醒来，发现待处理的一条或者同时存在若干条消息，就按顺序地将其发到事件处理器，将消息解析成完整命令。整个事件分派体系如下图：

拿到解析好的命令后，redis 内核再直接串行操作内存里的数据结构，比如读写 SDS、跳表、ListPack 等。

最后一步，才是把结果返回到客户端。

所以说，redis 内核在最关键、最容易产生冲突的数据真实读写上，是严格单线程串行的，所以叫做单线程模型，由于全部在内存操作，因此相比起 MySQL 这种数据存储在磁盘的数据库，速度非常之快。

Redis 4.0 后

Redis 4.0 后，增加了异步现场，能够独立于主线程后台作业，但主要也是用来大 Key / 大集合异步释放（UNLINK、ASYNC 清理）及刷盘/关闭等后台任务这种操作，并不直接涉及内存里底层数据的读写。

所以，虽然引入了异步线程，但最关键的数据读写上还是主线程亲自操刀，所以说本质上还是单线程模型。

Redis 6.0 后

Redis 6.0 引入了网络多线程，主要应对监听 socket、响应等网络操作，依然没有改变主线程直接读写数据等局面，所以仍然是单线程模型。

Redis 持久化

Redis 的读写全部发生在内存，一旦 redis 退出、重启，数据全部丢失，因此 4.0 后引入了持久化 RDB，可以按照时间节点将内存制作成快照存入磁盘，或者从磁盘将快照加载到内存。

持久化的方式

持久化有两种主要方式：RDB 和 AOF，派生出三种持久策略：RDB only、AOF only、RDB+AOF。

RDB，就是定时将内存写为快照；

AOF，和 MySQL 的 mvcc 体系差不多，记录每条指令的读写，粒度从固定宏观时间缩小为单条指令。

RDB+AOF，则是官方推荐的策略，

持久化策略可以在 redis 主动配置，包括是否持久化、使用哪种策略。

RDB

RDB 本质上锁某一时刻全量数据的二进制压缩快照，以 .rdb 文件存在磁盘。

前面提到了，RDB 是定时任务（时间可配置），时间一到就要制作快照，但一个问题是 redis 是单线程模型，制作快照难道也要主线程来制作吗？针对这个问题，redis 给了两种方法：save 主进程串行制作、bgsave fork 一个子进程后台异步制作。

注意，是 fork 一个进程而非线程。我们前面提到，redis 是单线程模型，本质上是在说 redis 进程内只有一个线程 MAIN，bgsave 之所以要 fork 子进程，而非拉一个子线程 SLAVE，是避免出现并行读写冲突：进程的内存由线程共享，MAIN 如果拉起一个 SLAVE，SLAVE 制造快照势必要获取当前所有内存的当前静态版本，如果 MAIN 在 SLAVE 期间写了内存，会导致内存数据与 SLAVE 欲获取到数据不一致。所以要 fork 进程，进程之间的内存是独立的，主进程将静态数据复制给子进程，随后主进程的读写就不再影响子进程，子进程可以放心地制造快照。

save 就是直接让主进程完成制作快照并持久化到磁盘的全过程，期间正常的客户端发来的读写命令会被阻塞，所以实践中几乎不用。

bgsave 就是 background save，主线程不亲自参与制作快照，但是 fork 另一个 redis 进程，让子进程来进行制作快照，为了 fork 子进程，主进程把自己的内存也一并复制到子进程内，所以 fork 子进程时会阻塞主进程，且数据量越大阻塞越久。

fork 带来的阻塞时间：

数据集大小 fork 延迟 额外内存占用 风险等级
< 1GB < 10ms ~10MB (页表复制) 低
1-10GB 10-100ms 10-100MB 中
10-50GB 100ms-1s 100-500MB 高
> 50GB > 1s > 500MB 极高

AOF

AOF 会将读写命令记录到日志和本地文件，每次重启加载数据时，本质上就是重放日志里的指令集，其记录流程如下：

  1. 读写命令执行后，写入 AOF 缓冲区；

  2. AOF 缓冲区的内容写入 AOF 文件（此时还在内存页 page 中）；

  3. 用 fsync 函数把内存里的 AOF 文件刷盘。

也就是说，在 fsync 前服务崩溃，内存中的数据有丢失的风险。

关于 fsync 的时机，redis 给了三个设置：

  1. always：每条命令刷盘一次。性能最不好，但是最安全。

  2. every sec：每秒刷盘一次，默认。性能、安全皆中等。

  3. no：linux 自己决定，一般是 30 秒。

AOF 重写

为了避免 AOF 文件无限膨胀，AOF 文件需要时常进行瘦身。

如何瘦身呢？比如我们在后端里经常用到短生命的缓存字段，这些字段在后端运行期间内会不断产生然后消灭，因此在 AOF 内也会不停地把这些指令写进去。但是仔细想想，百万千万条早就死亡的字段的 set 与 del 占据了海量的空间，虽然都是忠诚地根据写命令一条一条写入的，但是对现在的 redis 而言屁用都没有，这些东西显然是可以直接去掉的。同理，这样瘦身的目的就是严格筛选出，有哪些命令是直接贡献当前内存的，只保留这些命令，形成一个新的 AOF 文件，这样就实现了瘦身。

所以，AOF 重写本质上是最少的指令重建当前集。

再来看看 AOF 重写的流程，在 Redis 7.0 后一直到现在的 AOF 重写：

  1. 主线程得知 AOF 要重写时，先把内存中用于存放指令的 incr 文件刷盘到磁盘，然后清空 incr。

  2. 还是主线程，fork 一个子进程，当然内存肯定也一并复制。主线程完事后，就继续处理读写了，指令当然也继续存放到全新的 incr。

  3. 子进程根据当前内存重建 AOF 文件，并且也要用 fsync 刷盘到磁盘用一个临时文件 tmp.aof 或者叫做base存起来，然后通知主线程自己搞完了，最后 die。

  4. 主线程阻塞后，一是把 base 与自己刚刚写的 incr 一起拼接、刷盘、覆盖为 mainfest(tmp.aof+incr)，作为新的 aof 文件，然后把 incr 清空，因为刚刚的 incr 只是 AOF 重写期间的临时新增指令，现已加入 mainfest。

不难看出，Redis 7.0 后的 AOF 重写，是基于 incr、base、mainfest 三个文件的，而在此之前，只有一个 apendonly.aof 文件，所以在子进程重建期间，主线程的新增写入都是存放到 AOF 缓冲区，直到子进程完事主线程接班时，继续将 AOF 缓冲区里的新增指令写入 appendonly.aof 并刷盘到磁盘。

Redis 缓存

三大经典问题

缓存穿透

缓存穿透：hacker 用一个数据库、reids 中都不存在值的字段访问接口，由于缓存 redis 中不可能存在，所以路由到数据库。这个现象主要会造成稳定的绕过缓存直达数据库，对数据库造成压力。

解决方案：

  1. 数据库中确认不存在该 key 后，直接缓存到 redis 以 null 形式存在。这种方式治标不治本，因为不能确保未来会不会真的有这个值的合法业务进来，因此只能把 ttl 设置的很短，这样又会造成大量无用缓存频繁创建和消灭。

  2. 布隆过滤器。

  3. 接口限流，甚至物理停机

缓存击穿

击穿，一般意味着因压力过大而破防，然后压力变得更大的现象。比如电压过高引发空气击穿等。

缓存击穿：热点数据缓存在 redis 中，不停承受高并发请求。若缓存此时失效，短时间内会有高并发请求同时打向数据库，造成数据库压力甚至崩溃。

解决方案：

  1. 永不过期，不推荐。

  2. 互斥锁，缓存失效时可以确保只有一个请求在查数据库。

  3. 提前预热，推荐。

缓存雪崩

缓存雪崩：大量缓存字段 ttl 截止时期相同，由于这些字段的请求总量过高，当这些字段同时失效时，请求全部自动打到数据库上，造成压力。

解决方案：

  1. 随机 ttl，总之避免短时间内大量字段的异常失效。

  2. redis 集群，避免只有一台 redis。

  3. 提前预热。

提前预热怎么做？

  1. 滑动过期：命中缓存时，若缓存字段剩余 ttl 太低，顺手重制；

  2. 逻辑过期+异步重建：不直接加 ttl，而是加一个字段 expireAt 用时间戳标识过期的时间。然后在这个缓存数据加两个入口：一个允许高并发正常读，另一个需要抢互斥锁，但是抢到了就可以重置这个缓存字段的 expireAt。所以，理想条件下这个数据只要一直有请求，那就一直不过期，比滑动过期来说普通请求不需要走一遍重置逻辑，更快了。

  3. 概率刷新：ttl 余额越小，重置的概率越大。

  4. 看门狗 watchdog，开一个进程专门续签热门 key。

hot key

如何发现 hot key？如何判定 key 是热点？主要有以下方法：

  1. redis 官方自带的，redis-cli --hotkeys 基于 LFU 统计 key 的访问频率； MONITEOR 事实显示所有指令，也可用于统计 key 频率。但是性能堪忧！

  2. 经验，例如大型活动，促销、秒杀等业务。

  3. 例如各种开源三方中间件，比如京东开源的 hotkey。

hot key 如何解决？前文中缓存击穿、缓存雪崩的限流是一种方法，但是如果要保证业务能够顺利进行呢？

首先是本地缓存，立竿见影，多的请求压根到不了 redis，但是缺点也很明显，一致性不好保证，所以一般配合短 ttl，这样够保证最终一致性。

然后，将一个 hot key 复制成多份，把发往同一个 key 的请求打散到其他地方，然而一致性保障更难了。

接下来是主从复制，把主 key 的 value 复制到多个从 key，让从 key 来响应请求，主 key 则异步更新从 key 的 value。当然，和本地缓存问题一样，实时一致性难以保障，读到旧 value 的概率增大。也适合

以上方法，由于都存在一致性难题，所以适合读多写少的 key。

那么写多的 key 呢？说实话没有银弹，高并发的写意味着极为艰难的一致性保障，而读多写少的情况下尚且难以保障，在写多的情况下就更难以保障了，不过写多的 key 一般不会放到缓存里，该老老实实查库就查库，老想着缓存反而是思维局限里。

Big key

就是 value 很大的 key，value 的尺寸极大：String 超过 10KB 就要警惕，超过 1MB 基本可以认定是大 key；Hash/List/Set/ZSet 元素个数超过 5000~10000，或总体积超过 10MB 就可以认定了。

大 value 会造成什么问题？Redis 是单线程模型，单个 key 的 value 过大，其读写势必会阻塞 redis 线程拉低整体性能；不仅是读写性能低下，持久化性能也会被拉低，因为持久化需要复制内存全量以 fork 子进程。

还有一个问题，既 hot 又 big 的 key，在高并发下很容易占满网络带宽，又或者直接把内存吃满然后崩溃。

如何解决呢？首先是拆分，把大 value 拆成多个小 key，这个很好想象。

然后是压缩，做 gzip/snappy/LZ4 压缩后再存，这个似乎是用 CPU 换空间？

最好的是从源头上解决，避免出现 big key。

三种缓存读写策略

旁路缓存

最常用的策略。

读数据时，先过 redis 缓存读，未命中才直接读库；写数据时，直接写库，然后再删 redis 里的旧缓存，等待接下来的请求读库然后把新的数据缓存。

这种方式尤其适合读多写少的情况。

一个问题，为什么要先写库，然后再删缓存？假如倒过来，先删缓存，再写库呢？假设高并发的情况下，你先把缓存删了，其他请求再进 redis 发现未命中，就直接读库，然后又把读到的数据缓存到 redis，但问题是，你还没有把新数据写到库里啊？等真的写库的时候，一切都来不及了，在你之后的所有请求，本质上读到的都还是旧数据，更厉害的是库里的新数据，和 redis 里的旧数据不一致了。当然，可以在写完库后延长一段时间再把缓存删了，保证库和缓存最终一致（别想什么强一致性，做不到），这就是延迟双删。

当然，必须要说的是，先写库再删也不能保证完全一致，写库完、到删 redis 期间依旧可能有请求读到旧数据。

有什么值得注意的？1.删除操作要有失败重试；2.延迟双删不能保证强一致性。

读写穿透

把 redis 看成主要库，redis 面向主要请求来源，写操作先更新 redis ，再一致地更新到数据库。

异步缓存写入

当要写数据时，直接写 redis 更新缓存，把更新的指令记到日志，当日志够数量后异步、批量地更新到数据库。

缓存淘汰与过期策略

这和 ttl 到过期有什么区别？我们知道 redis 是纯内存读写的，一般来说内存够的时候确实只有 ttl 能主动淘汰缓存，但问题是内存不够时，肯定需要清退策略，这里所说的淘汰与过期策略，就是决定哪些缓存可以被淘汰以换取空间的策略。

并发 & 分布式

Redis 事务

前排提醒，这个很鸡肋，不建议实际使用。

Redis 允许在 MULTI 和 EXEC 命令中，插入一批命令，且保证这批命令顺序执行完成，当 EXEC 按下后，事务才真正开始执行。

Redis 事务的问题在于，它只能保证顺序执行，也就是不被插队；另外，他也不提供回滚等手段，如果事务执行到一半 redis 挂了，就没办法恢复了。

所以，reids 事务更像一个批处理入口，而非 mysql 那种严格安全的事务。

WATCH

WATCH 能保证一个 key 被其他指令修改时，事务全体失败。原因在于，事务只有在 EXEC 按下时，才完全不插队地执行，前面 MULTI 后的命令，本质上还是要在 redis 事务管理区里面排队，这意味着什么呢？意味着事务还在安排期间，其中的数据可能被修改。

Lua 脚本

WATCH 虽然不是锁，但是起到了一个乐观锁的作用，也即相信事务期间数据不会被其他事务干扰。但是，这样还是太鸡肋了，所以 redis 引入了 lua，这是一种能够随便嵌入的轻量级语言。

具体怎么做？lua 脚本可以伪装成一条 redis 读写命令，redis 单线程开始执行时，搭建 lua 环境，然后把 lua 脚本交过去执行，然后开始耍起啥也不用做，等执行完了拿到结果，再返回给客户端。整个过程中，redis 不允许执行其他命令，因为要保证不存在请求竞争，等到 lua 脚本执行结束后才能继续，所以说 lua 脚本能保证原子性。

不过话虽如此，lua 也不能回滚恢复，redis 崩溃，数据该丢还是丢。

另外，一般来说 5s 中无应答就直接杀掉 lua 进程，所以 lua 也不能无限阻塞 redis 单线程

分布式锁

Redis 作为分布式锁时，一般是希望能保持仅有一个请求进入特定服务，这种情况下就是正确性锁，比如严格的扣款、锁库存操作；而如果只是希望用于减少性能消耗，允许同时存在多个持有锁的请求，也不会造成任何数据损失，那么就是效率锁，比如缓存重建等。我们一般针对正确性锁，设计分布式锁。

如何加锁？简单，一条 SET lock <唯一值> NX PX 30000 就行，nx 表示不允许覆盖，px 设定过期时间，唯一值一般用 uuid 即可。为什么不要用 setnx 然后 expire，就是防止 expire 失败导致锁永生。

如何解锁？请求完成服务后，自然需要在服务内把锁删掉，但一个问题是，如果在服务进行期间锁就过期了，其他新来的请求会拿到新的锁，然后也进入服务，此时，你删掉的是谁的锁？删了其他人的锁，显然不行。所以需要校验是否是这个请求最开始拿到的锁，也就是为什么，set lock 需要一个唯一值，就是用来判断是谁的锁。

当然，删除期间也要用 lua 脚本，因为 lua 脚本可以阻塞 redis 单线程，从物理上就排除期间内锁过期删除（ttl 过期引发的删除也是 redis 单线程来删）、新锁建立的情况。

可重入锁

用信号量的可重入锁，抢锁的逻辑没什么区别，主要区别在于如何安全解锁。

可重入锁用 Hash 存，里面每个 kv 对用 唯一标识-重入次数 存储（注意，也要用 ttl），请求解锁时（当然，注意使用 lua），先看里面有没有自己的标识，有的话再看重入次数是不是大于 0，如果都满足，则重入次数减 1。如果减完后次数不大于 0，则刷新 ttl；如果减完后次数为 0，则跟一般分布式锁一样，直接删掉就行。

Redisson 里面 lock 和 unlock 一一对应，也是同样的道理。
