AI Coding 实践 - 以写一个论坛项目入手

发表于2026-11-07|更新于2026-11-13
|阅读量:

AI Coding 从 vibe coding 到 spec coding，再一步步发展到 Harness Engineering，已经有了众多实证，正确使用 AI 非但不会带来破坏，反而带来了增益，相信每一个使用过 AI 的开发者，都无法回到古法编程了，AI 的开发效率就是高于人类，人类没有必要否认，更没必要对抗，所以问题已经转变为：怎样使用 AI 写出我们想要的代码？每个开发者有自己的工作流，也有自己的理解，不必分个高下，只要能实现需求交付那就是好的。

我本人在26年3月接触过当时还是最佳实践的 superpowers + gstakc 构成规划、执行、验证的工作流，但是后来将精力投入到其他去了，后面出现的 trace、审计这些完全没有接触过了，所以对 AI Coding 实践算是重新开始学习，我的想法是使用 AI Coding 从立项到真实上线，完成一个类贴吧论坛项目，全程不自己写一行代码，找到适合自己的 AI Coding 实践方法。

项目之前

在项目开始之前，我想尽可能地表达一下我目前对 AI Coding 如何写出可靠代码这个问题的理解。

打铁还需自身硬

使用 AI 写需求的前提是本人得懂需求，也看得懂代码，不要求看得懂每一行，最起码要看得懂 AI 代码在抽象层面是如何工作的，我在开发的时候也会尽量观察 AI 写完的代码，看看逻辑是不是通顺，是不是符合现有规范，也就是说 AI 的每一步要尽可能地在我的掌握之下，所以我会尽可能缩短 AI 单次编写的范围，防止变动范围太大我看不过来，也方便 git 回滚。

grill-with-docs

grill-with-docs 是我必用的一个 skill，它的作用相当于增强 AI 的思维链吧，有的 AI 不擅长将需求转化为技术方案，这个 skill 强制进行，而且考虑得很全面，虽然有时候给你列大几十个点很烦，但很多时候很好用。

而且，这个 skill 全程作用，在规划完成的执行、评审阶段，也能按照规范，同时主动发现问题、给出解决方案。

文档维护

md 文档可以做到很多事情，作为项目长期记忆可以固定很多事实，统一各种术语；作为计划书可以补充思维链和上下文，但是文档太多反而分散注意力，所以长期记忆只留一个；技术文档在实现之后要及时清理，可以删除，也可以移动到工作区外备份（通常没啥用），只要不让 LLM 看到就行。

为什么技术文档要及时清理，这其实是我很早之前就发现的一个问题，一个大型项目是一个 session 完全无法承接的，不同的实现通常由不同 session 进行，而不同 session 拥有的上下文不一样，这就导致：不同 session 不管是上下文还是读写的文档，如果没有做版本控制，极大概率产生前后冲突，污染上下文；就算事实之间没有冲突，LLM 频繁地尝试读取这些文档，也会造成上下文占用、执行效率降低、分散注意力等问题。而有什么需要的，直接让 LLM 读代码就行了，很多人会维护很多这样那样的 spec，却忽略了代码本身就是最权威的 spec。

测试

事实证明，AI 很喜欢各种 tdd 单元测试，实际上很没有用，我会在项目中明令禁止单元测试，而是使用 e2e。

审计

这一块我自认为不擅长，我以前经常使用 /review ，但是我后来发现效果并不是很好，很多时候只是简单地看看代码就完了，不做更深的测评。

后来我完全摒弃了大部分 skill，重要的地方回归人工，当然，AI 先跑一下 e2e 测试，先最低成本地发现一下问题，一直到 AI 声称完全跑通的时候，我再上场作为一个用户测试。

当然，我这个最后一环测试的深度肯定没有 AI 那么严密，只能找找明显的错误，更深层次的错误只能依靠最后全链路测试。

pi

为什么使用 pi？pi 是当前轻量化 Coding Agent 的巅峰，其设计哲学是尽可能减少 Harness，让 LLM 自由发挥，其内部只内置了 4 个基本工具，也不内置 skill，这样的好处是适配各种模型，坏处则是模型的能力被无限放大，很多时候任务效果好坏，由模型性能直接决定。

而 cc、codex 这些产品走得是另一条路线，它们针对自家模型进行了优化，比如将工具 Schema 等喂给自家训练模型，这导致自家模型用起来就如鱼得水，其他家的模型没有经过专门训练过的话，用起来就很难受。国产的各家模型厂商也在不断迭代适配自家模型的 Agent 产品。

不过值得单独提及的是 dsh，它以 ds 命名却完全不对 ds 做适配，技术路线反而比 pi 更激进。

所以，我全程使用 pi + ds flash 1017 进行开发。

关键点在于，这套方案对吗？我的做法是，让它自己对抗性审查一遍，看看哪些地方有冗余，哪些地方不够清晰，一般能够作出合理的调整。

但是，我必须说的一点是，reflection 有反思滑坡的风险，很有可能反而把正确的方案改错；加上这种立项开始的技术评审本身就有很大的调整空间，不像项目已经进行中的物理限制大；再加上模型本身性能问题……那么答案只有一个了：自己过一遍方案。

其实也没什么好说的，架构技术栈选择尽可能贴合主流，然后澄清业务需求，这样其实就差不多了，更具体的在后续实现的时候再详细探讨，AI 给出的全局方案做个参考就好，只要开发主动权掌握在人手里，后续就可以慢慢调整。

P0.5

P0.5 对需求环节，依旧让它回答三个问题：要完成哪些任务？怎么推进？怎么验收？

pi 的回复：

  1. 搭建 ts 前端骨架。

  2. 支持 404 页面、layout 渲染等。

  3. 定好与后端的契约，比如我们就确认了一项，返回码一律只含传输层意义，例如：业务成功和业务失败，都返回200，因为 200 代表消息传输成功，而失败/成功则采用额外字段响应。

    更多的契约：

    情况 判定 行为
    成功 HTTP 2xx 且 body.code === 0 返回 body.data
    业务错误 HTTP 2xx 且 body.code !== 0 抛 ApiError(code, message)
    未登录 HTTP 401 走 onUnauthorized 钩子（P0.5 里是空实现），再抛 ApiError
    限流 HTTP 429 抛 ApiError，不自动重试
    网络/超时 — 抛 ApiError('NETWORK')

  4. 确认前端可以收到后端 Result 结果。

  5. 编写首页，能够使用 react 组件显示服务状态。

  6. 部署上线

验证码的生命流程的？验证码就是 6 位的随机数字，用户输入 email 并点击发送验证码后，后端服务先生成 6 位验证码，并将 前缀+email & 验证码 以键值对形式存入 redis。当用户提交表单时，触发消费验证码，如果验证码无误，那么通过后端逻辑，redis 中也删除键值对。

另外有几点：

  1. 验证码发送后，在 redis 中根据 email 存一个键值对，存在 60 秒，用来判断是不是发送过于频繁；

  2. 相同 ip 地址的发送验证码请求，一小时内有限制，同样是通过在 redis 中存一个 ipKey 实现；

  3. 消费验证码时，如果验证码不对，会在 redis 中存储并累积 tryKey，超过一定数量时，该验证码就失效。

用户注册成功后，就可以顺理成章地在 mysql 内存一个对象。

双 token 机制

p1.2 是整个 p1 的重点，涉及到用户登录状态和 session 的实现，正好，我们复习一下用户登录和分布式 session 的原理，真拿你没办法，坐好喽。

我们都知道，对于用户而言，登录只需要账号和密码，后端验证好后就放行，但是后端怎么验证一个用户是否已经登录呢？简单，在一个地方保存一个东西例如 usr_id_login = true，表示用户已登录就行，这个就是最简单的 session。

但问题是，这样一来后端只知道某个用户是否已经登录，无法知道，但用户在登录状态时，进行各种各样的操作，例如评论、购物等操作，后端不知道发送请求者的身份，怎么在后台操作？照理来说很简单啊，请求上加一个 userId 不就行了？这样确实后端知道了，但是这是一个很大的安全隐患，那我是不是只要知道其他用户的 userId 或者其他唯一信息，是不是就可以调接口随便操作别人的账户了？显然不能这么设计。

所以我们引入 RS256，用户登录后，后端签发一对私钥密钥，后端保存私钥，公钥 access 交给各个服务，每次用户进行操作的时候，请求都带一个 access，只有和后端的密钥签发机构对上了，这次的操作才合法。

不过，问题又来了：access 也有可能泄漏啊，一旦泄漏，只要在用户登录期间，攻击者可以随意操控账户。解决办法是：定时过期刷新。access 定时过期，后端重新签发一个 access 就行了。不过这种方式真的实现安全了吗？别忘了一切接口调用都要 access，包括续签 access！也就是说，攻击者拿旧的 access 就可以主动续签新的 access！也就是说理论上攻击者可以无限持续泄漏。

所以，我们引入双 token：access token 和 refresh token：access 用来请求业务，存在时间短；refresh 代替上一种方法的续签，而且只能用于续签，存在时间长。当 access 失效时，后端验证 refresh 而非 access，如果对得上，就重新发布 access 和 refresh，也就是旧的 access、refresh 均失效。

这里划线的三个，不就是上面 session 吗？所以 auth:session:jti 实际表达了两件事：1.同一个用户不同ip、设备登录的数量；2.该用户目前可用的 access。

然而 access 是会过期的，在存 redis 时就约定了 access 的存活时间为 2 小时，当 redis 中 access 过期时，不会主动通知后端，而是用户携带该 access 向后端发送请求时，后端才会发现这个 access 已经过期了，然后就进入重新签发 access 流程，后端会查询 mysql 中的 refresh 表，拿到其中的 jti 字段发给签发服务重新签发，对 refresh 表中，真正的 refresh token 其实时 jti 字段，其行本身的 uuid 只用于内部识别，这也是一种安全举措。

另外不得不提的一点是，refresh 也有泄漏的风险，如果攻击者获得了 refresh token 撑过了两小时，access 肯定会过期，对于用户来说，走正常的签发流程，用旧的 refresh 获得新的 access 和 refresh，但是攻击者的 refresh 仍然是旧版，倘若再次使用，后端会检测到该 refresh 已经过期了，于是得出结论：本次登录有可能不安全，于是将该用户直接下线，攻击者获取的资源全部失效。即便是攻击者先获取 refresh，也会导致用户的 refresh 是旧版，从而同样会造成下线。

但是，我们为新旧 refresh 设置了 30s 的缓冲期，也就是新 refresh 签发后的 30s 内，旧 refresh 也可以正常使用（更古老的 refresh 不行），这是由于用户正常使用有可能造成两个 refresh，比较两个页面刷新时 access 失效，两个页面刷新请求都要走签发流程，先一个进入后端的获得新 access 和 refresh，后一个则来不及，如果直接认为登录不安全将用户下线，肯定是影响体验的，所以设置 30s 的缓冲期。

很大一圈，但过。
